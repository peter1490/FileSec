Date: 2026-10-01. Baseline: `6cc22d5da56df8368fb82fdcb989522667cff66f`
(`Release v0.4.4`). The worktree was clean at the start.

## Conclusion

**Do not treat v0.4.4 as having a clean security or recovery audit.** The existing
cryptographic primitives and many defensive checks are well chosen, and the test
suite passes, but this review found reproducible rollback, migration, suite
selection, state-consistency, and extraction defects. Five findings are rated
High below. These ratings describe engineering impact under stated conditions,
not CVSS scores or a claim that an unauthenticated Internet attacker can exploit
every issue.

The most urgent work is to prevent rollback-backend downgrade, authenticate the
migration confirmation, make identity migration recoverable, retain hybrid
protection during direct transfer, and serialize persistence across processes.
The largest measured remaining UI problem is quadratic trash-model preparation.

This is a source-level engineering audit with executable checks and inspection of
published artifacts. It is not an independent cryptographic certification, formal
protocol proof, exhaustive penetration test, or guarantee of complete security.
Application code was not changed or remediated during this audit.

## Scope and Method

The inventory contained 101 tracked files, including 55 Rust files and three
workflows, with approximately 33,400 lines of source, tests, scripts,
configuration, and documentation. The review covered all three crates, every
core and GUI module, all tests and fuzz harnesses, dependency policy and the
locked graph, packaging, both installer variants, release automation, and the
existing guides and security documents. Binary assets were considered for
embedding, references, and licensing, not as a visual-design audit.

The large application module was reviewed through its actual end at 9,503 lines,
including workers, networking UI, render paths, helpers, and inline tests. The
store module was reviewed through its actual end at 1,766 lines. Earlier audit
documents were treated as claims to verify, not proof. Unsubstantiated review
hypotheses were discarded.

The public production deployment is a desktop release, not a hosted service.
The public latest release was v0.4.4, published 2026-09-07 at 08:59:22 UTC, with
17 assets: 14 installer/archive artifacts, two SPDX inventories, and a checksum
manifest. All 16 payload assets were downloaded and matched the manifest.
Downloaded applications and installers were not executed.

Evidence labels used below:

- **Reproduced:** an isolated probe observed the behavior in this checkout.
- **Artifact verified:** the behavior or metadata was inspected in a published artifact.
- **Source confirmed:** the controlling code and failure sequence were traced; the corresponding platform, race, or crash was not executed.
- **Known residual:** the repository already documents the limitation; it remains unresolved.

## High-Priority Findings

### FS-01: Backend Selection Can Disable Secure Rollback Protection

Owner: [store.rs](../crates/filesec-gui/src/store.rs#L1247).

`select_anchor_backend` trusts the unauthenticated `.state-anchor-backend` file.
When its value is `degraded-v1`, the function selects file-backed anchors without
consulting an existing OS anchor. A filesystem tamperer can replace that marker,
remove or restore the file anchor set, and present older, individually valid
state. The protection promised against filesystem-only rollback is bypassed
without modifying the OS keychain or forging a state signature. The degraded
warning does not turn this into an authenticated recovery decision.

An isolated execution of the actual selection function, with OS storage mocked
as available and populated, produced:

```text
before=SecureStorage after=DegradedFile secure_lookup_during_downgrade=0
```

Remediation: establish backend provenance outside the tamperable directory.
Never honor an unauthenticated secure-to-file downgrade. Require an explicitly
authenticated recovery operation if an established secure backend must change.
Test marker replacement, deletion, malformed values, and keychain unavailability
with already-protected state. This is distinct from the documented limitations
of a store that was deliberately file-backed from its creation.

### FS-02: Migration Confirmation Replaces Rather Than Verifies the Passphrase

Owners: [app.rs](../crates/filesec-gui/src/app.rs#L3875) and
[store.rs](../crates/filesec-gui/src/store.rs#L1203).

The upgrade dialog asks for the passphrase to confirm migration. Its value is
passed to `migrate_to_hybrid`, which creates the replacement keystore under that
value without first unlocking the existing keystore with it. A typo becomes the
new passphrase. The user is told that the passphrase is unchanged, and existing
passkey/device slots are discarded by the fresh keystore creation.

An isolated store probe used a valid original passphrase and a different supplied
confirmation:

```text
migration_succeeded=true
original_passphrase_works=false
mistyped_passphrase_works=true
```

Impact: unexpected credential change and potentially permanent lockout on the
next launch. This is not presented as a deliberate password-change workflow.

Remediation: authenticate the current keystore with the supplied confirmation
before any migration write, compare its identity to the active session, and
preserve the existing passphrase semantics. Reject a wrong confirmation without
changing files, slots, or anchors. Add a wrong-passphrase migration regression.

### FS-03: Identity Migration Is Not Crash-Safe as Documented

Owners: [store.rs](../crates/filesec-gui/src/store.rs#L1158),
[store.rs](../crates/filesec-gui/src/store.rs#L1203), and
[store.rs](../crates/filesec-gui/src/store.rs#L552).

Migration first bridges containers, then removes every old-identity anchor,
then creates and saves the new keystore, contacts, registry, and hardened vaults.
An error after anchor removal leaves the old state without its high-water
history. Errors after keystore replacement can instead leave the new identity
with protected records still bound to the old fingerprint. Decryptability by
both classical keys does not make those protected records acceptable: normal
loading rejects the fingerprint mismatch. The GUI returns an error without a
durable migration-resume workflow.

The early failure was reproduced by injecting invalid KDF parameters at the
public migration API's keystore-creation stage:

```text
memory cost must be non-zero
anchors_before=3 anchors_after=0 old_keystore_unlocks=true
```

The GUI normally supplies valid parameters; this probe deterministically tests
the same ordering that RNG, storage, or later I/O failure can expose. It is not
a claim that the GUI accepts externally supplied KDF parameters.

Remediation: validate and authenticate all prerequisites first. Retain old
anchors until a durable migration journal can resume both identity namespaces.
Stage and validate new protected records and vaults, record completion, then
retire old state. Inject failure at every step, including after the new keystore
is durable but before contacts, registry, or vault hardening completes.

### FS-04: Direct Transfer Does Not Preserve Hybrid Protection

Owners: [sender.rs](../crates/filesec-gui/src/net/sender.rs#L104),
[format.rs](../crates/filesec-core/src/format.rs#L117), and
[transport.rs](../crates/filesec-core/src/transport.rs#L117).

The sender always selects `ExportOptions::default()`, which is `Classic`.
Neither a hybrid source vault nor two hybrid-capable peers changes this choice.
The outer handshake is also classical. An isolated export using the exact sender
options and two hybrid identities observed:

```text
source=Hybrid output=Classic
```

Impact: the configured hybrid KEM/signature protection does not travel with the
data. Re-encrypting under the recipient's hybrid local store does not change the
recorded transfer. The transfer secret contributes additional security; this
finding is not a demonstrated current plaintext-recovery attack or a formal
analysis of the protocol's post-quantum strength.

Remediation: select the hybrid container suite when both identities support it,
and require an explicit, informed compatibility decision for a lower suite.
Keep the outer handshake's classical limitation accurately documented. Add a
hybrid loopback test that inspects the received transport container's suite,
not only the recipient's at-rest suite or byte-for-byte payload.

### FS-05: Persistence Coordination Is Not Interprocess

Owners: [store.rs](../crates/filesec-gui/src/store.rs#L148),
[store.rs](../crates/filesec-gui/src/store.rs#L316), and
[store.rs](../crates/filesec-gui/src/store.rs#L354).

Each `Store` owns an independent `Mutex`. The complete `AnchorSet` is loaded,
changed, and saved as one blob, without an interprocess lock or compare-and-swap.
Two instances can both load an old set and overwrite each other's changes. An
anchor for one object can consequently disappear or regress when another
object's set is saved. State-file writes and anchor checks/commits also are not
held under one cross-process transaction, permitting same-epoch forks or a file
whose commit fails after replacement. Both installed application variants use
the same underlying data store, making multiple instances a realistic case.

Evidence is source-level; a deterministic multi-process stress test was not run.
The backend dependency itself warns that simultaneous Windows credential writes
are not ordered reliably.

Remediation: enforce a single active writer per canonical store, or hold an OS
interprocess lock across state read, candidate calculation, file commit, and
anchor update. Re-read under the lock. Test two processes changing distinct
objects and the same object, plus interruption between data and anchor commits.

## Additional Security and Recovery Findings

### FS-06: Windows Anchor Storage Has a Small, Unhandled Capacity Limit

Owners: [store.rs](../crates/filesec-gui/src/store.rs#L316) and
[autounlock.rs](../crates/filesec-gui/src/autounlock.rs#L174).

All object anchors are serialized into one keyring credential. Windows permits
at most 2,560 bytes in `CredentialBlob`; `keyring 3.6.3` enforces that limit.
Serialized arrays of real FileSec anchors in the probe occupied:

| Vault anchors | Array bytes, excluding the outer set |
|---|---:|
| 1 | 255 |
| 4 | 1,014 |
| 8 | 2,024 |
| 16 | 4,038 |
| 32 | 8,073 |

Exact sizes depend on serialized byte values and object IDs. Keystore, contact,
registry anchors, and the outer set add more. A modest number of vaults can
therefore prevent future anchor saves. New vault creation has already created
its directory before that failure is returned.

Remediation: use bounded per-object credentials or a bounded secure root
commitment over authenticated external records. Add a capacity-limited fake
backend and native Windows tests well beyond the first few vaults.

Reference: [Microsoft CREDENTIALW documentation](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw).

### FS-07: Windows Auto-Unlock Is Not Guaranteed Device-Local

Owners: [autounlock.rs](../crates/filesec-gui/src/autounlock.rs#L49) and
[Cargo.toml](../crates/filesec-gui/Cargo.toml#L118).

`DEVICE_BOUND` is true on Windows, and the UI/documentation promise local-machine
storage. The selected `keyring 3.6.3` Windows backend writes generic credentials
with `CRED_PERSIST_ENTERPRISE`, not `CRED_PERSIST_LOCAL_MACHINE`. Microsoft
documents that enterprise persistence can make credentials visible on other
machines for users with roaming state. Anchors and auto-unlock tokens use this
same backend.

This does not establish that every Windows account roams, or that a token alone
decrypts data without the corresponding keystore. It does invalidate the
unconditional device-local guarantee.

Remediation: use explicitly local-machine persistence, or remove the guarantee
and show an accurate platform warning. Test actual persistence policy and roaming
behavior; do not infer device binding from the platform name.

Reference: [keyring Windows implementation](https://docs.rs/crate/keyring/3.6.3/source/src/windows.rs)
and the Microsoft documentation linked above.

### FS-08: Failed Vault Reseals Leave a Mutated Reader

Owners: [format_v2.rs](../crates/filesec-core/src/format_v2.rs#L698),
[format_v2.rs](../crates/filesec-core/src/format_v2.rs#L745), and
[format_v2.rs](../crates/filesec-core/src/format_v2.rs#L847).

Mutations change `self.manifest` before its sealed replacement succeeds.
`state` and `view` are refreshed only after the write. A failed reseal can leave
different in-memory representations and disk state. A later successful mutation
can persist the earlier operation that was reported as failed.

The probe temporarily made the manifest destination a directory:

```text
returned_error=true same_reader_reads_new=true reopened_reader_reads_new=false
later_mutation_persists_failed_write=true
```

Remediation: mutate and seal a candidate, then swap all reader state after a
successful commit. Clean up uncommitted staged blobs. Test failure for every
mutation, including a later successful operation on the same reader. GUI cloning
reduces some exposure but does not repair the public core API's contract.

### FS-09: Extraction Can Silently Lose Case-Colliding Files

Owners: [vault.rs](../crates/filesec-core/src/vault.rs#L190),
[format.rs](../crates/filesec-core/src/format.rs#L1116), and
[format_v2.rs](../crates/filesec-core/src/format_v2.rs#L635).

Distinct logical paths are accepted even when the destination filesystem aliases
them. A vault containing `Report` and `report` extracted successfully on the host
filesystem but produced one file, containing the second entry's content.
Unicode-normalization aliases present a related portability risk, but that
specific case was not runtime-tested here. The prior audit already acknowledges
case/Unicode aliases; this is an unresolved data-preservation defect, not a new
discovery of the general limitation.

Remediation: preflight extraction for destination-equivalent paths before
writing. Define a portable normalization/collision policy or fail with a clear
conflict report. Preserve both source entries and the user's existing outputs.
Test case-insensitive and normalization-sensitive destination filesystems.

### FS-10: Blob Reclamation Assumes Unenforced Directory Durability

Owners: [safe_io.rs](../crates/filesec-core/src/safe_io.rs#L113),
[format_v2.rs](../crates/filesec-core/src/format_v2.rs#L813), and
[format_v2.rs](../crates/filesec-core/src/format_v2.rs#L881).

After syncing the temp file and renaming it, `SafeFileWriter::commit` ignores
parent-directory open/sync failures and returns success. V2 overwrite/remove
then unlinks superseded blobs. If the manifest rename is not durable but blob
reclamation survives a crash, the remaining manifest can reference a deleted
blob. An anchor may detect the inconsistent state, but cannot recover deleted
content. This is a conditional crash-durability risk; it was not power-loss tested.

Remediation: retain superseded blobs until durable directory-entry commit is
known, or use a durable journal plus deferred garbage collection. Merely
returning an error after rename is insufficient: the rename may already have
occurred. Add filesystem fault injection and interrupted-commit recovery tests.

### FS-11: Registry and Vault Operations Can Diverge

Owners: [app.rs](../crates/filesec-gui/src/app.rs#L2578),
[app.rs](../crates/filesec-gui/src/app.rs#L2649),
[app.rs](../crates/filesec-gui/src/app.rs#L3726), and
[store.rs](../crates/filesec-gui/src/store.rs#L831).

Creation/import writes the vault before its registry record. Deletion removes
the vault before persisting registry removal. A later registry or anchor error
leaves an undiscoverable vault or an entry for deleted data while the UI reports
failure. Startup cleanup handles migration scratch directories, not registry
reconciliation. Migration `.migrate-tmp` files and completed-but-unregistered
directories can also survive interruptions.

Remediation: add a durable operation journal, stage creations, use recoverable
tombstones for deletion, and reconcile on startup. Test errors after each durable
step. Keep encrypted remnants recoverable instead of deleting them blindly.

### FS-12: A Captured Hello Replays the Proof Gate

Owner: [transport.rs](../crates/filesec-core/src/transport.rs#L622).

The MAC binds the initiator ephemeral and nonce, but no listener replay state
rejects the exact same validated message. Two fresh responders with the same
active transfer secret accepted an identical captured `Hello` and each produced
a fresh `Auth`. That `Auth` includes the responder identity and signature in
cleartext. Possession of a captured proof is therefore enough to trigger this
disclosure and asymmetric work, without current knowledge of the secret.

This does not complete the new session, reveal the initiator's private key, or
decrypt transferred contents. Fresh responder contributions prevent replaying
the old confirmation. The impact is narrower privacy/proof-gate and availability
behavior during the lifetime of an unchanged listener secret.

Remediation: add a bounded, expiring replay cache scoped to the active secret,
or redesign the pre-disclosure proof around a responder challenge. Test exact
Hello replay separately from the existing replayed-Auth test.

### FS-16: File Paths Still Accept Visual Format Controls

Owners: [vault.rs](../crates/filesec-core/src/vault.rs#L190) and
[app.rs](../crates/filesec-gui/src/app.rs#L6348).

Identity display names are sanitized, but the path validator accepts bidi
override/isolate and zero-width format characters. The probe accepted the Rust
string literal `"report\u{202e}gpj.exe"`. Entry names are rendered directly and
later become actual filesystem names. Their presentation in OS file managers,
dialogs, and external applications can be misleading. Acceptance is verified;
an exact deceptive GUI rendering was not demonstrated in egui.

Remediation: reject dangerous format controls in portable vault paths, or render
them visibly with directional isolation and an unambiguous real extension.
Test both application display and extracted names. A valid sender signature
does not make a filename truthful or safe to open.

### FS-17: Rate-Limiter Memory Has No Hard Ceiling

Owners: [concurrency.rs](../crates/filesec-gui/src/net/concurrency.rs#L104) and
[listener.rs](../crates/filesec-gui/src/net/listener.rs#L206).

Failed IPs are stored in an uncapped `HashMap` and removed by age. Five-minute
retention bounds time, not entries or bytes. Sustained real connections from
many addresses can grow it with arrival rate; ordinary off-path TCP spoofing is
not enough. This is a low-priority resilience gap, not a demonstrated single-IP
authentication bypass.

Remediation: impose a maximum cardinality with expiry-aware eviction and,
where appropriate, IPv6 prefix aggregation. Test sustained unique-address churn.

## Production and Distribution Findings

### FS-13: Official macOS Portable Executables Are Not Developer-ID Signed

Owners: [release.yml](../.github/workflows/release.yml#L126) and
[package_macos.sh](../packaging/macos/package_macos.sh#L53).

The portable archive is created before packaging. The packaging script copies
the executable into an app bundle and signs the copy, leaving the archived
original unchanged. Inspection of the published standard archive confirmed:

```text
Signature=adhoc
TeamIdentifier=not set
```

The standard DMG and PQC DMG do carry Developer ID signatures and both have valid
stapled notarization tickets. Their signing gates are not silently bypassed.
The portable executable's ad-hoc signature is not publisher identity signing,
even though its checksum matches the release manifest.

Remediation: sign the distributable executable before archiving, or distribute
the same signed/notarized app bundle in the portable archive. Verify every macOS
distribution format after packaging, not just the DMG.

### FS-14: Release Publication Does Not Depend on CI Security Gates

Owners: [release.yml](../.github/workflows/release.yml#L317) and
[ci.yml](../.github/workflows/ci.yml#L3).

The publish job depends on version, builds, and SBOM generation. It does not
depend on tests, lint, or `cargo audit`/`cargo deny`. The separate CI push trigger
is for `main`, while release runs on tags. A tagged commit can therefore build
and publish even if its CI checks failed or never ran. Shipped all-feature tests
also run only on macOS in CI; Windows/Linux jobs test the default feature graph.

Repository-side tag protection and approval policies were not accessible to this
audit, so this is a workflow-level missing gate, not a claim that the maintainer
currently publishes arbitrary unreviewed commits.

Remediation: invoke reusable validation from the release workflow and require it
before publishing. Test the actual shipped features on all three operating
systems. Require protected release approvals for the tagged commit. Pin the Rust
release toolchain and runner baseline where reproducibility matters; `stable`
and `*-latest` still float despite Action SHA pinning.

### FS-15: The Windows PQC Binary Omits a Required DPI Workaround

Owners: [build.rs](../crates/filesec-gui/build.rs#L30) and
[build.rs](../crates/filesec-pqc/build.rs#L18).

The standard build embeds a system-DPI-awareness manifest specifically to avoid
the documented winit window-growth loop on Windows 11 24H2 when moving between
monitors with different scale factors. The PQC build script embeds only its icon.
Inspection of both published portable executables confirmed DPI manifest strings
in the standard binary and none in the PQC binary.

This is a deployment/UI regression risk, not a cryptographic vulnerability.
The actual multi-monitor symptom was not exercised on native Windows.

Remediation: share the required application manifest between both build scripts,
verify resource type 24 in each final executable, and exercise mixed-DPI monitor
movement on Windows. Do not make required runtime metadata merely best-effort.

### FS-18: Third-Party Notices Need Distribution Review

Owners: [theme.rs](../crates/filesec-gui/src/theme.rs#L184),
[Inter-LICENSE.txt](../crates/filesec-gui/assets/fonts/Inter-LICENSE.txt#L54),
[Phosphor-LICENSE.txt](../crates/filesec-gui/assets/fonts/Phosphor-LICENSE.txt#L1),
and [release.yml](../.github/workflows/release.yml#L126).

The application embeds Inter and Phosphor fonts, whose license terms require
notices to accompany distributions. Both published macOS and Linux portable
archives and both Windows zips contain only their executable, not the checked-in
notice files. The MSI notice component is disabled. Debian packages contain an
auto-generated project copyright file, not a packaged third-party notice bundle.
`cargo deny` checks allowed licenses, not compliance with redistribution terms.

Remediation: generate a reviewed third-party notice bundle and include it in
every installer/archive or expose complete, readily viewable notices in the
application. Confirm whether embedded font metadata satisfies the applicable
terms; this audit does not make a legal infringement determination.

## Optimization Audit

### O-01: Trash Model Is Still Quadratic, Even Outside the Trash View

Owners: [app.rs](../crates/filesec-gui/src/app.rs#L5518),
[app.rs](../crates/filesec-gui/src/app.rs#L8394), and
[app.rs](../crates/filesec-gui/src/app.rs#L8404).

Every browser frame snapshots all entries and computes `trashed_items`, even
when showing live files. For each trashed directory, `trashed_subtree_totals`
rescans every entry. Work is $O(n \times t)$ for $n$ entries and $t$ trashed
directories. Visible-row virtualization does not reduce this model work.

The actual unchanged helper functions were extracted and compiled with
`rustc -O`. Each directory had one child file; every result's counts and sizes
were checked. Median of three runs on this host:

| Entries | Trashed directories | Model time |
|---|---:|---:|
| 2,000 | 1,000 | 2,938 us |
| 10,000 | 5,000 | 40,345 us |
| 20,000 | 10,000 | 151,512 us |
| 40,000 | 20,000 | 621,642 us |

This measures only the helper, not total frame time or I/O. The larger cases are
already too slow for responsive main-thread rendering.

Remediation: compute subtree aggregates in one indexed pass and cache the trash
model by manifest revision. Calculate detail rows only when needed. Add a
trash-heavy preparation benchmark; the existing benchmark and virtualization
test primarily cover ordinary browser rows and paint output.

### O-02: Frame Preparation Clones and Reindexes Unchanged Metadata

Owners: [app.rs](../crates/filesec-gui/src/app.rs#L5518),
[app.rs](../crates/filesec-gui/src/app.rs#L8154), and
[app.rs](../crates/filesec-gui/src/app.rs#L4503).

Normal row preparation has already been improved to one child-count pass and
cached sort keys. Nevertheless, each browser frame clones paths, constructs a
live-entry set, rebuilds child counts, filters, and sorts again. An active
transfer handle, including listening, schedules repaint every 200 ms.

Remediation: cache immutable entry/index data by reader revision, and view rows
by directory/query/sort. Use event-driven repaints for unchanged listening state;
keep bounded progress/spinner scheduling for genuinely active work. Measure
model preparation separately from visible-row paint count.

### O-03: Bulk Changes Repeat Manifest and Anchor Commits

Owner: [store.rs](../crates/filesec-gui/src/store.rs#L852).

Append/remove/rename loops reseal the whole manifest and update the complete
anchor set after each individual change. Bulk imports or moves therefore incur
repeated serialization, encryption, fsyncs, and secure-storage calls. Entry
lookup and implied-parent creation also repeatedly scan vectors. Blobs are
streamed efficiently, but metadata work is not simply constant per changed file.

Remediation: introduce a bounded batch mutation at the owning vault abstraction,
with one candidate manifest and one durable epoch/anchor transition. Maintain a
path index for existence and parent-type checks. Preserve fault recovery and
atomicity while optimizing; do not remove the source length/hash verification
introduced by the earlier audit. Benchmark thousands of small files and moves,
not only a single large streaming file.

### O-04: Bounded Inputs Are Not an Application Memory or Disk Budget

Owners: [format.rs](../crates/filesec-core/src/format.rs#L49),
[format_v2.rs](../crates/filesec-core/src/format_v2.rs#L77), and
[listener.rs](../crates/filesec-gui/src/net/listener.rs#L49).

Manifest ciphertext may reach 512 MiB and manifests may contain ten million
entries. Ciphertext, decrypted bytes, decoded structures, indexes, and GUI
snapshots can coexist. The 64 GiB inbound-transfer limit also is not a free-disk
reservation. These substantial limits are already disclosed by the prior audit.
No RSS or disk-exhaustion stress run was performed here.

Remediation: define realistic desktop metadata and process-level budgets,
preflight available disk space, and include concurrent/malformed-input RSS tests.
Keep streaming APIs for bulk data; in-memory materialization intentionally scales
with plaintext size. Avoid claiming that every operation uses only one chunk of
total RAM: that excludes metadata and deliberate in-memory APIs.

## Lower-Priority Hardening and Policy

- [keystore.rs](../crates/filesec-core/src/keystore.rs#L126) reconstructs PQC public/seed pairs without re-deriving public keys; incomplete pairs silently disappear. Reject inconsistent authenticated backups rather than accepting identities that later fail hybrid operations. This requires a crafted authenticated bundle and is not an unauthenticated ciphertext bypass.
- [store.rs](../crates/filesec-gui/src/store.rs#L454) can establish an absent anchor before successful unlock. A self-signed replacement keystore can poison an empty file-backed/cold-start namespace. Delay first-anchor establishment until unlock and fingerprint comparison succeed. Existing trusted anchors still reject a different identity.
- [app.rs](../crates/filesec-gui/src/app.rs#L2918) clones quick-editor plaintext into an ordinary worker `String`, while the editor itself has scrubbing behavior. Use a zeroizing worker payload. This is hygiene, not a claimed defense against the explicitly out-of-scope live-memory attacker.
- [vault.rs](../crates/filesec-core/src/vault.rs#L149) and [format_v2.rs](../crates/filesec-core/src/format_v2.rs#L727) do not require an existing ancestor to be a directory. The probe accepted both `a` as a file and `a/b` as a child. Enforce tree validity in builders and both manifest validators before extraction or UI use.
- [app.rs](../crates/filesec-gui/src/app.rs#L7293) intentionally permits offline export to unverified contacts after a warning. This is not a hidden bypass; consider a separate explicit per-export override listing fingerprints, rather than treating a warning as trust establishment.
- [mod.rs](../crates/filesec-gui/src/net/mod.rs#L338) ignores two padding bits in the transfer code and filters non-alphanumeric characters broadly. Enforce canonical padding and accepted separators. Generated secrets still have 128 bits of entropy; alternate spellings are not an entropy break.
- [listener.rs](../crates/filesec-gui/src/net/listener.rs#L236) holds a handshake permit through receipt/import. Release that resource after authenticated admission while retaining the separate single-transfer guard. This is bounded capacity tuning, not an unbounded worker defect.
- [ci.yml](../.github/workflows/ci.yml#L56) uses `stable` rather than testing the declared minimum. Add an explicit MSRV job; Linux's newer effective toolchain requirement must remain accurately documented.
- [fuzz.yml](../.github/workflows/fuzz.yml#L89) does not run with a tracked fuzz lockfile. Commit an independent fuzz lockfile and use locked execution if reproducible fuzz dependency resolution is required. The detached fuzz workspace should stay outside ordinary release builds.
- The published release API reports `immutable=false`. Evaluate immutable releases and protected tags/approvals. Checksums alone do not authenticate a mutable checksum manifest; consumers should verify provenance.

## Controls Positively Checked

- Strict Ed25519 verification and non-contributory X25519 rejection are present; hybrid containers require both signatures when that suite is actually selected.
- Suite/header binding, independent blob keys, chunk authentication, empty-blob authentication, and truncation/reorder/tamper regressions are covered by the passing tests.
- KDF upper-resource checks happen before Argon2 allocation; malformed/oversized imports and strict bounded CBOR decoding have targeted tests.
- The manifest and file path chokepoints reject traversal, absolute paths, malformed blob IDs, Windows device names, alternate streams, and several portable aliases.
- Private exclusive temp creation, per-file authenticated extraction, atomic replacement, and symlink/hardlink cleanup regressions passed. The documented path-race limitation remains.
- Passkey ceremonies request user verification/PIN, and tests pin their argument policy. Physical authenticator behavior was not validated.
- Network offer and signed-container sender identities are checked against the authenticated peer; frame deadlines, cancellation during reads, frame caps, worker bounds, and declared-size checks have passing tests.
- Sender packetization and progress reporting are bounded more carefully than the historical implementation. NAT mappings use finite leases and attempted cleanup; real-router interoperability was not tested.
- All 34 Action references across the three workflows are SHA-pinned. Script syntax, actionlint, and ShellCheck passed. Valid version metadata succeeded; a mismatched tag and missing required macOS signing were rejected.
- Official Windows signing code and official DMG notarization fail closed for missing credentials. Earlier suspicions that these paths silently permit missing required signing were rejected after reading the actual scripts.
- Standard and PQC packages have distinct binaries, installer identities, MSI upgrade codes, and archives. MSI is per-machine, whereas NSIS is per-user; that distinction should remain documented.
- Published Debian packages have version `0.4.4-1`, declare `libc6 >= 2.39`, and include the expected D-Bus/udev dependencies. Older glibc distributions are not supported by these artifacts merely because the archive is called portable.
- Published SPDX files are valid SPDX 2.3 JSON, with 546 and 547 packages. They describe broad resolved dependency inventories, not a verified list of only code linked into a particular OS binary.

## Remaining Assurance Limits

- Native Windows/Linux execution, Credential Manager capacity and roaming, hostile filesystem races, mixed-DPI monitor behavior, and installer upgrade/uninstall workflows were not run on those operating systems.
- Physical FIDO2 devices, real routers/NAT traversal, prolonged network load, disk-full recovery, and actual power-loss durability were not tested.
- Windows signature blocks were inspected, but Authenticode chain/revocation validation was not performed. macOS notarization ticket checks do not replace native app launch and installation testing.
- The GitHub CLI was unavailable; published SLSA attestations were not independently cryptographically verified. Matching the manifest and API digests is not equivalent to provenance verification.
- Repository branch/tag protections, approval environments, signing-secret access policies, and the organization's certificate lifecycle were not accessible.
- The custom handshake, hybrid combiner, and encrypted formats still warrant independent cryptographic review. Library primitives plus passing tests do not prove protocol composition.
- Existing exclusions remain: full endpoint compromise, live memory scraping, physical erasure guarantees on SSD/CoW media, and the documented narrow filesystem TOCTOU boundary. External editors may retain their own plaintext copies.

## Remediation Order

1. Block FS-01 and add authenticated backend-recovery tests.
2. Fix FS-02 before exposing migration as a passphrase-preserving operation.
3. Implement a resumable migration transaction for FS-03 and interprocess persistence coordination for FS-05.
4. Preserve hybrid container protection in direct transfers for FS-04.
5. Resolve Windows anchor capacity/device-binding behavior and failed reseal state; add cross-platform failure-injection coverage.
6. Preflight extraction aliases and journal registry/blob reclamation operations.
7. Gate publishing on validation, sign macOS portable output, share the Windows DPI manifest, and package reviewed notices.
8. Remove quadratic trash preparation, cache metadata views, and batch durable mutations with correctness tests.
9. Revisit dependency exceptions with owners/deadlines and run native platform, hardware, router, and recovery testing before making stronger release-assurance claims.

Preserve the original encrypted data and current anchors before recovery or
migration work. Do not clear anchors or discard quarantined state as a general
repair strategy.
